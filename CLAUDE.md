# Smash & Dash

How to reach the running game (launch, remote eval in skalang, screenshots, replays): @AGENTS.md

Pokémon fan game with real time battles, built on the ska engine (`external/ska`, with skalang in `external/ska/external/skalang`). The game is a library (`libGame`) loaded by the engine launcher `ska_main`.

## Build and run

```sh
cmake -S . -B build && cmake --build build -j8
LD_LIBRARY_PATH=build/lib build/bin/ska_main   # from the repository root (the game data and the "wd:" scripts are relative to it)
```

The build compiles every script (`smash_and_dash_scripts_check`): a script error fails the build, with its file and line.

Build time: about 2 min clean at `-j8` (6 cores, 12 threads: more jobs barely help), seconds for a game file, more for an engine header (included everywhere). The game sources compile while the engine links (object libraries `smash_and_dash_objects`, `smash_and_dash_worldgen`), the C++ standard headers are precompiled (ska `SKA_PRECOMPILED_HEADERS`), ccache is used when installed.

Battle simulation: `SAD_BATTLE_AUTOPLAY=1` makes the battle AI play the Pokemon of the player too; the debug log traces the battle (`Battle t=...`: decisions, skills used, hits, misses).

Script tests, headless (no window): `cd build && ctest`. They are `tests/*_test.miniska` (assertions: `Test = import "bind:std.native.test"`), run with the templates of the engine and game functions (default bodies) and the fakes of `tests/fakes` (ex: the engine keeps the game variables, `setNextRandom` chooses the random values). Add a test with a script change when the script has logic (rules, AI, helpers).

Web (browser, WebAssembly): `tools/web/build.sh [build-web]` (needs the Emscripten SDK: `source <emsdk>/emsdk_env.sh`, or `EMSDK=<emsdk>`; the first build builds the SDL3 libraries for the web), then `tools/web/serve.sh` serves `build-web/game/bin` to the local network (`http://<address>:8000`). The page is `src/web/shell.html`: it keeps the saves (`Data/Saves`) in the browser (IndexedDB). On the web: no thread, the browser calls each frame (`GameCore::run`), the renderer is WebGL (`opengles2`: the world and screen shaders as GLSL ES 1.00, `Shaders/<name>.frag.es`, drawn by ska with WebGL), the game files are packed in `index.data` (the directories listed in `src/CMakeLists.txt`). The engine side is `external/ska/cmake/SkaWeb.cmake`. Online: each push on master builds it and publishes it on GitHub Pages (`.github/workflows/pages.yml`: https://scorbutics.github.io/SmashAndDash/).

Linux CI: `.github/workflows/linux.yml` (Debug and Release builds and the script tests, in an Ubuntu 26.04 container for its SDL3 packages).

Shaders: GLSL fragment shaders in `src/shaders/*.frag`, compiled during the build to `Shaders/<name>.frag.spv` (ska `ska_compile_shaders`, needs `glslangValidator`), loaded with `ska::Shader{ "./Shaders/<name>" }` (ska README "Shaders"). They need the SDL3 `gpu` renderer natively; on the web ska converts them to GLSL ES 1.00 (`cmake/SkaShaderEs.cmake`: `<name>.frag.es`, packed with the page) and draws the world and the screen through them with WebGL (`SDLRenderer::drawThroughWeb`; not the shaders of single drawings). Ex: `battle.frag`, the post-processing of the battles (`GUIBattle`).

## Scripts

Read [SCRIPTING.md](SCRIPTING.md) (where scripts start, the functions given to them) and `external/ska/external/skalang/doc/LANGUAGE.md` (the language) before writing a script. The syntax differs from Ruby, JavaScript and Python. Keep skalang's rules: strong static typing, no implicit conversion, no null value.

- The generator is being ported to C++ (`src/src/Game/Gameplay/World/Generation`, plain C++ : it will make the world of a new game in the game, native and web), stage by stage, checked bit for bit against the Python one: `tools/worldgen/golden.py > tests/worldgen/golden.txt` (after a change of the Python generator), `ctest -R sad_worldgen`. Done: the noise, the climate (biomes, relief), the height before the villages; the villages (sites, growth, names), the distance to them, the biome weights and the mixes of the corners (`WorldPlan`); the roads (A*), the terrain (grounds, terraces, cleaned), the stairs, the places (`Terrain`); the tile of each block of the three layers (a tile is the text of its Python key), the blocks walked on, the villages decorated, the trees, the signs, the items, the rooms, the events, the light (`Layers`: the shapes of the drawn structures come from `Resources/Worldgen/shapes.txt`, `tools/worldgen/shapes.py`; the room templates are `Resources/Worldgen/rooms`). the chipsets (`Chipset`: the tiles drawn in each biome by Python, their collision masks (`tile_mask`, the `.png.mask` of each chipset: the solid parts of the tiles, 4 x 4 cells a tile, from the materials of their drawings: the rim of a cliff, a trunk; the walls of the game are these parts, ska README "Maps and tilesets"), `Resources/Worldgen/tiles.png` at one pixel per voxel, made by `tools/worldgen/atlas.py` after a change of the drawings or of the keys; C++ blends them per corner as PIL does and fills the cells; `Png`: a PNG reader and a BMP writer, plain C++). the files of a world (`Files`: the PNG writer deflates, a world is about 15 MB) and the worlds of the saves, generated by the game (`SaveSlots`, the title screen `StateTitle` and its loading screen, a step of `worldgen::WorldWriter` per frame; `SAD_SAVE=<name>` skips the title, `SAD_WORLD_SEED`; about 5 s, native and web). The Python generator stays the reference (the tests: `golden.txt` sums up every file of its seed 7 world). The tiles are being repainted in 3D (the identity of the game: toon tones, ink, a watercolour wash, the palette of Cube World): `tools/render3d` (three.js in headless Chromium, `npm install --prefix tools/render3d`; the look in `style.js`, an asset a scene of `scenes/`, the projection of the map: a view with `oblique`), `tools/worldgen/paint.sh` renders `scenes/tiles.js` for each biome into `Resources/Worldgen/painted/<biome>` (the same geometry in every biome, only the colours) and remakes the atlases: a painted tile replaces its voxel drawing (`tilegen.painted`), the C++ reads it at 48 px from `painted.png` (`TileImage`: 16 voxels or 48 pixels). Every tile is painted, in the Okami look chosen by the user (`tools/worldgen/paint.sh` renders with `brush=1`: outlines that swell and taper, sumi ink, parchment; cast shadows, `view.shadows`; the painted patterns of `S.toon`: grass strokes, dirt, cobbles, bricks, plaster, planks, seamless with `period: 1`; the reference design: `scenes/proposal.js`): `scenes/tiles.js` (trees, tall grass, the grounds), `tiles_cliffs.js` (a view per cliff and cliff foot key: pale boulders, the layout of the voxel cliffs kept, their collisions from the voxel scene), `tiles_village.js` (the structures: `stamp_<name>`), `tiles_objects.js` (the objects, the posts, the animated tiles), `tiles_rooms.js` (the rooms, meadow palette), the colours in `scenes/tones.js`; the ground tiles and the water banks are composed from the painted textures in Python (`painted_ground`); a drawing of tilegen/rooms is replaced by its painted image when there is one (`_painted_or`, `stamp_image`, `scene_image`); `painted.png` packs about 5400 cells (39 MB decoded), a world about 9 s. The interface (`tools/tilegen/ui.py`): parchment panels framed by a sumi brush stroke, `Ui::Ink` sumi. The world on the screen goes through `Shaders/paper` (`PaperLook`, ska `Renderer::setWorldShader`: the world only, not the interface; `SAD_PAPER` 0 .. 2, 0 off; on the web too: `?SAD_PAPER=`). `tools/render3d/render.mjs` keeps Chromium's temporary files in `build/tmp` (`/tmp` has a quota per user). Then `TMPDIR=build/golden-tmp tools/worldgen/golden.py > tests/worldgen/golden.txt` (it writes a world in the temporary folder).
- The infinite world (the worlds of the game, `WorldVersion` 11: a continuous world, 512 x 512 chunks, generated region by region, 8 x 8 chunks, as the player walks; the ocean a part of it): its reference is `tools/worldgen/infinite.py` (every value a pure function of the block and the seed; `check`: a region alone equals itself generated after its neighbours; `map`: the shape of the world; `tiles`: a region built in two windows, the same files). The C++ port, bit for bit (`tools/worldgen/golden_infinite.py > tests/worldgen/infinite.txt`, about 4 min, `ctest -R sad_worldgen`): `Generation/Infinite` (the climate with fixed rank tables and a majority filter, the continents and the ocean: shallows, deep water, reefs, sand bars, chains of islands; the villages, a site at most per cell of 144 blocks; the roads, each village to its 2 nearest, an A* in a box; the terraces cleaned and their stairs by bounded passes in a window `Apron` blocks wider), `Generation/Region` (`RegionBuilder`: a region built by the stages of the finite world, `World` on a window, `RegionOptions`; about 2 s), `Generation/InfiniteFiles` (`InfiniteWriter`: the chunks written on demand, the rooms of a region named by their door `w_room_<x>_<y>`; `InfiniteWorldWriter`: the loading screen), the game `World/Chunks/ChunkGenerator` (a thread natively; on the web a worker, `World/WorldWorker` → `world_worker.js`: the data of the generator sent once, a chunk at a time written there and its files sent back, `Chunks/FileBundle`; a chunk wanted at once, a warp, is written in the page; with `--fixed-step` in the steps of the game) used by `WorldStreamer`. The draw priorities of the world are from the top of the camera (ska `DepthPriority`: the world y is about 475000 px). The ocean: reefs (`obj_reef`, rocks out of the water), deep water (`obj_deep_<v>`, darker waves), the chunks mostly sea with their wild Pokemon (`SPAWNS` "ocean": Carapuce, Roucool, on the islands and sand bars). Next: sea Pokemon of their own (their data and sprites: Tentacool, Magicarpe...), the C++ composing the ground and cliff tiles.
- The maps are generated, a world per save, by the game in the save (`<save>/World/`, from `[World] seed`: SCRIPTING.md, "The world"); `tools/worldgen/worldgen.py --seed 7` writes the same world in `Data/Worlds/seed7/` (out of git; 8 x 8 chunks of 40 x 40 `w_*`, rooms `w_room_*`, a chipset per map in `Chipsets/`, biomes from a climate as in Minecraft, blended at their borders) (the game reads the maps of a save in its world: `[World] directory`, `MapDirectory` in `SavePaths.h`). `save1`: seed 7, `save2`: seed 42. Change the generator, not its output. A new kind of tile goes in the tile room too (`tools/worldgen/tileroom.py`, AGENTS.md), with its depth (`tile_base` in `worldgen.py`: flat, or how many blocks lower its object stands; written in `tiles.txt` and in the `.prop` of each chipset, the drawing order of the engine: ska README "Maps and tilesets"; a change of the format of the worlds: `worldgen::WorldVersion`, the older worlds of the saves are generated again). The chunks `w_*` are played as one map, streamed around the player (SCRIPTING.md "The chunks": `Gameplay/World/WorldStreamer`, `ChunkEntities`, the plain C++ of `World/Chunks`, `ctest -R sad_chunks`; the web worker `World/ChunkWorker`). No story, no characters: only the capability scripts (`Levels/*.miniska`: surf, ledges, teleport, healing, shop, dialog, signs, items to find, rest beds).
- Map events: `<save>/World/<map>/<map>E.txt` (generated); the scripts they start stay in `Levels/`. Tile scripts: `Resources/Chipsets/tile_scripts/` (copied into the `Scripts/` of each generated chipset by the generator).
- The functions the game gives to the scripts are C++ modules in `src/src/Game/Script` (`game.dialog`, `game.character`, `game.map`, `game.party`, `game.interface`, `game.battle`), each declared by a template in `src/scripts/game.<name>.miniska`. Change the template with the C++ binding.
- A script only imported by other scripts (no `run` function) is listed in `GAME_SCRIPT_MODULES` (`src/CMakeLists.txt`).
- The texts are UTF-8 (the scripts, the data, the C++ literals, the worlds). `¤` is a line break in a message.

## Boundaries

C++ (ECS systems) owns the per frame work: the player walks freely on the map (8 directions, its physics body at its feet against the walls, corner sliding, the walls it pushes against touched: `Gameplay/Control/GridMovementSystem`; its gaits: the walk, the run and a pose between them (setting off, pushing off, braking), the animation state machines linked in `WorldState` (ska `Run`/`PoseAnimationStateMachine`, the 9 columns of its sheet: `Graphic/CharsetSheet.h`, `tools/tilegen/character.py`); its bob, squash and dust: `WalkFeelSystem`; the first Pokemon of the team able to fight follows it on its trail, a drawing without physics, away while it surfs and during the battles: `FollowerSystem`; the camera leads its walk: `ExploreCameraStrategy`), the characters walking around (`wander`, `patrol`) and the scripted steps (doors, surf, ledges) move block by block (walls from the physics shapes; the wild Pokemon charge or flee the player by their attitude, `WildPokemonComponent`, and a battle starts when the trainer and one touch: `FightStartSystem`; they arrive flying in or out of a hideout, a drawing on a path then a wild Pokemon: `ArrivalSystem`; where they land, which hideout: the script `Data/Battle/arrivals.miniska`, started by `WorldState::spawnOne`), freely in battles; the drawing shows the entities between their last two logic states (`ska::FrameClock`); the real time battle simulation (`Gameplay/Fight`, a fighting game: each fighter has a `FighterComponent` (its side, its current opponent: the nearest one standing, who plays it, its attack, stun, K.O., cooldowns) iterated by `BattleDirectorSystem`, `BattleSystem`, `FighterSystem` and the skill systems; `BattleStage` shares the battle-wide state (time with its hit stops, arena, feedbacks, sounds, which fighter is the player's) with them and `GUIBattle`; `BattleHit` applies a hit (damage, `BattleEffects`: stat stages and statuses); the intro and the outro (`StateFight` tasks: `LeapTransition`, `PokeballTransition`; `BattlePhase::Outro`: the recall, the experience bar; then the map goes on without loading: `MapEvent::resume`, and the removed fighters are parked out of the physics space, which keeps their bodies); `BattleCameraSystem` moves and zooms the camera (the world is drawn zoomed below `WorldInterfacePriority`, the interface is not: `DrawableContainer::setWorldZoom`)): skills, movements, hits, end of the battle. The battle rules and the AI of the wild Pokemon are scripts (`Data/Battle`, called through `BattleRules`, each with a C++ fallback: `rules` statistics, damage, types, the softer hits of the wild Pokemon, the capture chance; `status`; `stages`; `encounters`; `skills` known; `rewards`; `ai`) : pure functions asked at events, never every frame (what applies every frame is asked when it changes and cached); the battle rolls the dice and gives them, so a seeded replay stays the same, the moveset of a Pokemon of the team is saved (`Fight/Moveset`: the skills of its level at first; the skills of its next levels are learned in the outro of `steps.miniska`, forgetting one when it knows 4: `Party.learnable`, `Party.learn`); the battle flow is scripted with `Battle.start`, the `battle.won` / `battle.lost` hooks and the steps of each battle (`Data/Battle/steps.miniska`: the director starts it at each step and waits for it; its banners, its dialogs). The screens that draw themselves each frame (the title `StateTitle`, the battle `GUIBattle`, the menu of the trainer `TrainerMenu`: the team, the bag, the options, the choices asked by the scripts `GameDialog.select`; Tab or M, Escape back) use `Ui::Canvas` (`Graphic/GUI/Canvas.h`: texts, fills, the panels and bars of the theme `Theme`, the images of `Menu/default_theme` made by `tools/tilegen/ui.py`; `Ui::Layer`, `Ui::ChoiceList` for a menu with the keys and the mouse); the dialogs (`DialogBox`: the `DialogEvent` of the scripts, of the start of a battle, of an item; the trainer waits while one is shown, as with the menu and during a battle: its controls are held, `HoldPlayerControls`: its `InputComponent` and `ScriptAwareComponent`, `EntityManager::hold`) and the debug panel (`DebugPanel`, F3) too: the game uses no ska_gui window. ska_gui does not fit them: no navigation with the keys (the web pad), its widgets keep their state while those screens change every frame (bars, shakes, banners that scale and fade, marks that follow the fighters, render effects). Scripts own the content and the sequencing: they call verbs and wait for their completion. A missing feature for scripts is a new verb in a game module (C++ and template), not polling from the script.
